# 3.0.0 — exploration notes (FSR 4 / pure DX12 AI)

Date: 2026-11-28. Status: **exploration only, no product code changed.**
The partial `src/media/dx12_video.h` draft was deleted again.

Goal for 3.0.0-beta: FSR 4 (latest) and a pure-DX12 AI path, with the current
DLSS-G worker/proxy hacks removed. Frame generation and neural rendering are
DX12-only; upscalers may run on DX11 or DX12. The UI must say so.

## 2. SDK / API facts

### FSR SDK 2.4 (downloaded, `third_party/amd-fsr/`)

- `api/include/ffx_api.h`, `dx12/ffx_api_dx12.h`
- `upscalers/include/ffx_upscale.h` — FSR Upscaling 4.1.2
- `framegeneration/include/ffx_framegeneration.h` — FSR FG 4.0.2 + swapchain
- `framegeneration/fsr3/include/ffx_frameinterpolation.h` — internal 3.1.6 API
- signed DLLs:
  - `amd_fidelityfx_loader_dx12.dll` (39 KB)
  - `amd_fidelityfx_upscaler_dx12.dll` (57.7 MB)
  - `amd_fidelityfx_framegeneration_dx12.dll` (29.7 MB)
- license: `docs/license.md` (MIT-style; signed DLL redistribution allowed with
  the SDK terms)

FSR upscaling context requirements:

- D3D12, SM 6.6 for FSR 4. SM 6.6 needs Agility SDK 1.4.9+ on the device.
  The current app creates the D3D12 device with feature level 11_0 and the
  inbox runtime; FSR 4 may be skipped unless Agility is shipped.
- Inputs: color (render size), depth (R32_FLOAT), motion vectors
  (R16G16_FLOAT), optional exposure/reactive/transparency; jitter, frame time,
  camera near/far/fov, `reset`.
- Video has no camera. Two options:
  1. zero depth + zero MVs + `reset = true` every frame → spatial ML upscale,
     no ghosting;
  2. NVOFA MVs + flat depth + no reset → temporal quality, but local errors
     can smear.
- FSR's public API is version-agnostic: on non-AMD it picks FSR 3.1.6.

FSR Frame Generation:

- The public `ffxDispatchDescFrameGeneration`/swapchain path is tied to a DX12
  swapchain (`ffxCreateContextDescFrameGenerationSwapChainDx12`). It can run
  "interpolation only" with `FFX_FRAMEGENERATION_FLAG_NO_SWAPCHAIN_CONTEXT_NOTIFY`.
- The non-swapchain 3.1.6 `ffxFrameInterpolation` API is internal and needs the
  whole `FfxInterface` D3D12 backend; not exposed by the signed loader.
- Therefore a clean FSR FG needs a DX12 presenter/swapchain anyway.

### Native DLSS-G without the worker (the important find)

A known-good NGX recipe exists (NVIDIA forums / MSFS reverse engineering):

- `NVSDK_NGX_D3D12_Init` with `nvngx_dlss.dll` + `nvngx_dlssg.dll` present.
- `NVSDK_NGX_D3D12_GetCapabilityParameters` → `DLSSG.MultiFrameCountMax`.
- `NVSDK_NGX_D3D12_CreateFeature(cmdList, NVSDK_NGX_Feature_FrameGeneration, params, &handle)`.
- Per frame set:
  - `DLSSG.CmdQueue`, `DLSSG.CmdAlloc`, `DLSSG.FenceEvent`
  - `DLSSG.Backbuffer`, `DLSSG.HUDLess`, `DLSSG.MVecs`, `DLSSG.Depth`
  - `DLSSG.OutputInterpolated`, `DLSSG.OutputReal`
  - `DLSSG.MustCallEval=1`, `DLSSG.IsRecording=1`
  - `DLSSG.MultiFrameCount` / `MultiFrameIndex`
  - `DLSSG.Camera*` (identity + FOV/aspect; `CameraMotionIncluded=0`)
  - `DLSSG.Reset`
- `NVSDK_NGX_D3D12_EvaluateFeature` once per generated frame; submit the list.
- No swapchain, no injected proxy, no extra window. This is exactly the pure
  DX12, in-process path 3.0 needs.

### NVOFA (motion estimation)

- `nvofapi64.dll` is already on the machine.
- Headers: `nvOpticalFlowCommon.h` (NVIDIA) + `nvOpticalFlowD3D12.h`
  (MIT, dxvk-nvapi). Both can be vendored.
- Flow: `NvOFAPICreateInstanceD3D12` → `nvCreateOpticalFlowD3D12` →
  `nvOFInit` → register D3D12 resources with fences → `nvOFExecuteD3D12`.
- Output: `NV_OF_FLOW_VECTOR` grid (1/2/4 px), S10.5 fixed point.
- The existing `nr/native/nvngx.dll` worker already does this (`NvOFAPICreateInstanceD3D12`,
  `NS_NVOFA_GRID`, `NS_NVOFA_COST`, stabilization and residual shaders). Its
  source of truth is the binary, but the API is documented.
- This is the reference for local motion in both DLSS-G and DLSS SR.

## 3. Current pipeline map (what exists)

```
RTP (chiaki) → OnVideo → encoded queue (2 at buffer 0 / 6 otherwise)
  → DecodeThread (D3D11VA, highest priority)
  → decoded frame queue (max 8)
  → TakeFrameOrdered(2) / TakeFrame(buffer)
  → PresentVideo()
      → [AI] DLSS SR (D3D12 + shared D3D11 textures, CPU RGBA in)
      → [AI] NR worker (external process, shared memory)
      → [AI] DLSS-G worker (external process, topmost window)
      → Presenter (D3D11 swapchain) or worker window
```

Current binaries: `veyla.exe` (GPUI shell), `veyla-engine.exe` (C++ engine,
D3D11 presenter), `veyla-classic.exe`, `veyla-legacy.exe`.

The AI path is **not** pure DX12:

- DLSS SR: D3D12 compute, but input is CPU RGBA uploaded through D3D11, and the
  output is a D3D11 texture sampled by the D3D11 presenter.
- NR: external `nvngx.dll --live` process. It is DX12 internally, but out of
  process and fed by shared memory.
- DLSS-G: same worker + a second topmost window; >2x uses `fg/winmm.dll`
  injected with `CreateRemoteThread` (`TEMU` hack). This is the main thing to
  remove.

## 4. Findings — frame generation and drops

### 4.1 Worker feed is over-subscribed and drops silently

`src/next/ai/dlss_fg.cpp`

- `Submit()` keeps only one pending job; if a new RGBA arrives while the worker
  is busy it is dropped and `dropped_` increments.
- `WorkerMain()` calls `NvDlssnr::Process()` synchronously. When process time
  exceeds the source interval, inputs are dropped; the output cadence becomes
  "whatever survived", which is the judder users see.
- There is no backpressure, no cadence estimate, and no cap on how long a
  worker call may run. `Collect()` uses a 4 s pipe timeout.

### 4.2 The reported FG numbers are dead in production

`src/media/nv_dlssnr.cpp` `Start()`

- The worker log is only enabled when `BRP_FG_LOG` is set; otherwise it goes to
  `NUL`.
- `DlssFg::PollLog()` reads `nr-worker.log` every second to parse
  `[fg] displayed ...` and `generated, ...`.
- With logging off, `displayed_fps_` and `actual_multiplier_` stay 0.

`src/next/shell/next_app.cpp` `PublishBridgeStatus()`

- `fg_ms` is hardcoded `0.0` (line ~4641), although
  `dlss_fg_->process_ms()` exists.
- `generated` is never published; `ui/src/model.rs` has `generated` but it is
  always 0.
- `nr_ms_` is 0 when NR runs inside the worker; the combined NR+FG time is in
  `dlss_fg_->process_ms()` but not exposed.
- `fg_dropped_` is not published at all.

### 4.3 Topmost/window problems

`DlssFg::FrameWindow()` / `Attach()`

- The worker window is set `HWND_TOPMOST`; `WS_EX_TOPMOST` remains even when
  hidden. The 1 s anti-topmost sweep only covers the shell window, not the
  worker window.
- `Attach()` enumerates windows by PID and takes the first visible, unowned
  one; helper windows can be mistaken for the presenter.
- `SetWindowLongPtrW`/`SetWindowPos` on another process's window is fragile;
  cross-process style changes are not guaranteed.
- Visibility is `foreground == app || foreground == worker`. In engine mode the
  foreground can be the GPUI shell, so the worker hides and
  `show_standing()` presents a stale frame.
- This is the "app stays on top / frame gen covers everything" class of bug.

### 4.4 Multiplier/proxy state is inconsistent

`src/next/shell/next_app.cpp` `EnsureDlssFg()`

- `options.inject_fg_proxy = multiplier > 2 && winmm.dll exists` and
  `proxy_runtime_ = options.inject_fg_proxy` are set before `Start()`. If
  injection fails, `proxy_runtime_` still reports true while the official
  runtime is loaded, so `(multiplier > 2) != proxy_runtime()` does not restart
  correctly.
- The worker can step down to a lower multiplier; the app keeps showing the
  requested one.
- `Start()` refuses > 2560×1440, so 4K + FG is impossible by construction.
  `settings.cpp` also warns for DLSS-G + 2160p.

### 4.5 Removal target

Everything in 4.1–4.4 disappears with the native in-process DLSS-G path:
one DX12 device/queue, NVOFA motion, offscreen `OutputReal`/`OutputInterpolated`,
our own pacing. No `nvngx.dll --live`, no `winmm.dll` injection, no second
window.

## 5. Findings — upscaling (DLSS SR / FSR)

### 5.1 DLSS SR is spatial-only

`src/media/nv_dlss_sr.cpp` `Process()`

- Zero depth + zero MVs + `NVSDK_NGX_Parameter_Reset = 1` on **every** frame.
  No temporal history. This avoids ghosting on a video, but throws away most of
  DLSS's quality advantage. With NVOFA MVs and no reset, quality would be much
  higher (at the cost of motion errors).

### 5.2 SR adds a frame of latency

- `Process(synchronous=false)` waits for the previous submission and returns
  the previous output; the current frame is submitted and returned next time.
- `sync_sr` is only true when `frame_buffer > 0 && fps <= 30` (line ~3810), so
  the default 60 fps / buffer 0 path is always one source frame behind
  (~16.7 ms) before present.
- In the FG path `Readback()` immediately waits for the current submission and
  maps a staging texture, so SR becomes synchronous there and copies 8–14 MB
  per frame over PCIe.

### 5.3 CPU upload/download per frame

- `UpdateSubresource(input11_, ...)` + `Flush()` + cross-API fence wait every
  frame.
- `ReadbackSlot()` does `CopyResource` + `Map` (blocking) and a row copy.
- `NeedsCpuPixels()` is true for any AI stage, so the decoder always does the
  D3D11 video-processor → staging → CPU RGBA path even for SR, which could
  consume the GPU texture directly.

### 5.4 Live-toggle cross-device bug

`NextApp::Apply()`

- A vsync change destroys and recreates `stream_presenter_` (line ~2550) but
  does not shut down `dlss_sr_` unless an SR setting also changed.
- The recreated presenter has a new D3D11 device; `dlss_ready_` is still true,
  so the old DLSS output texture is used as an SRV on the new device. This is
  invalid and can show a black frame / debug-layer error.
- The new DX12 presenter must invalidate all AI contexts on recreation.

### 5.5 "Native" output is not native

`EnsureDlssSr()`

- `sr_output = Native` + quality < 5 falls into `out_w = 2560, out_h = 1440`.
  So "Native" at quality 4 renders 1440p, not the window/display size. The UI
  label and the code disagree.

### 5.6 `sr_model` is decorative

- `EnsureDlssSr()` ignores `ai.sr_model`; DLSS is always used. FSR needs a real
  backend branch (and the UI value must matter).

### 5.7 Failure is sticky and noisy

- Any `Process` failure sets `dlss_failed_` for the session and toasts each
  failed frame. A transient device/format issue disables SR until re-watch.

## 6. Findings — decode, duplicates, pacing

### 6.1 Duplicate frames are still presented

`NextApp::PresentVideo()`

- `PullFrame()` sets `new_frame = true` for duplicates too.
- The early-out is `if (!new_frame && !redraw_needed_) return;` — it never
  checks `video_frame_.duplicate`.
- Consequence: a 30 fps game streamed at 60 fps is re-uploaded and re-presented
  60 times/s, despite the comment claiming the last image is left on screen.
  It also defeats the "don't push an untouched backbuffer" intent.

### 6.2 Duplicate detection is unreliable

`Decoder::SampleFrameHash()`

- 64 rows × 64 columns of RGB (4k samples out of 2M). Small motion can miss
  every sample → a different frame is classified as duplicate.
- Exact equality is also wrong for compressed video: a repeated frame is not
  guaranteed bit-identical after decode.
- On the GPU path `out.duplicate = false` unconditionally, so duplicates are
  never detected when AI is off.

### 6.3 60-on-60 has no phase lock at buffer 0

- `PullFrameRaw()` at buffer 0 calls `TakeFrameOrdered(out, 2)` on every loop
  wake; the loop is woken by `WaitForFrame(2)` and presents immediately.
- If two decoded frames arrive inside one refresh, both are presented; the
  second replaces the first in the flip queue. The first never reaches scanout,
  but `present_misses` does not count it (PresentCount advances faster than
  refresh).
- There is no display-phase gate, no queue target, and no "one present per
  refresh" rule at buffer 0.

### 6.4 Encoded-queue overflow triggers an IDR per drop

`Streaming::OnVideo()`

- Queue is 2 encoded units at buffer 0. On overflow it pops the oldest and
  calls `chiaki_session_request_idr()` immediately.
- A sustained decode deficit turns into an IDR storm: keyframes are large,
  bandwidth spikes, more drops, more IDRs. Needs a rate limit / backoff.

### 6.5 CPU-pixel flag is a data race

- `cpu_pixels_` is a plain bool written on the UI thread and read on the decode
  thread. Benign on x86 in practice, but UB; make it atomic.

### 6.6 Buffer > 0 pacing is better but can oscillate

- Adaptive `buffer_target_` increments on drought and decrements every 5 s;
  `playout_trim_` is a PI loop clamped to ±2 %. Worth keeping but needs a
  hysteresis test.

## 7. Findings — UI / settings / packaging

### 7.1 The requested note is not present

- No AI page says "DX12 only". The note must be added to:
  - Frame Gen page: *Frame generation runs on DX12 only.*
  - Neural page: *Neural rendering runs on DX12 only.*
  - Upscaling page: *Upscaling supports DX11 and DX12.*
  - Diagnostics capability cards.
- `next_app.cpp` capability text currently says "Capabilities are file checks.
  DLSS SR and DLSS-G run in Watch." — needs a DX12 statement.

### 7.2 No FSR state anywhere

- `SystemInfo` has `dlss_sr`, `dlss_fg`, `nr_worker`; no `fsr_sr`, `fsr_fg`,
  `fsr4`, `nvo`, `dx12`.
- `Status` (Rust) has `dlss_sr_ready`, `dlss_fg_ready`; no FSR fields.
- `PublishBridgeStatus()` publishes no FSR fields.

### 7.3 Backend values

- `AiBackend` enum: `None, DlssSr, DlssFg, NvidiaVfg` (`src/next/core/types.h:44`).
  Add `Fsr` / `FsrFg` or use string `sr_model`/`fg_backend`.
- `ai.sr_model` default `"dlss"`; `ai.fg_backend` `"none"/"dlss-fg"`.
- `settings.Validate()` hard-codes DLSS assumptions:
  - DLSS-G + 2160p warning (worker cap) — obsolete with native FG.
  - DLSS-G expects `sr_model == "dlss"` — wrong for FSR FG.

### 7.4 Optimize is NVIDIA-only

`ui/src/app.rs` ~580:

- `nvidia = gpu.contains("nvidia")`, `sr_ok`/`fg_ok` only DLSS.
- AMD users fall to "no AI". Must detect AMD/Intel and select FSR, with the
  FSR4 vs 3.1.6 fallback surfaced.

### 7.5 Diagnostics lies

- `fg_ms` = 0, `generated` = 0, `nr_ms` = 0 with NR in the worker.
- "Frame age" is measured from packet arrival, good, but the SR one-frame delay
  is not included in the present-lag number.

### 7.6 Packaging

- `tools/package_release.ps1` does not copy `amd-fsr` DLLs. Add
  `amd-fsr\runtime\{loader,upscaler,framegeneration}.dll` + license.
  ~87 MB installed; the delta from `_floor-2.7.0` will include them.
- `README.txt` template and CMake version are 2.7.2; bump to 3.0.0.
- `make_update.ps1` hashes all files; the 57 MB upscaler adds build time but is
  fine.

### 7.7 Version parsing handles betas

`VersionParts("3.0.0-beta1")` → `[3,0,0]`, so beta and final compare equal.
The updater prefers stable over prerelease (`kind 2 > 1`); with
`update_channel = 1` a beta is selectable when no newer stable exists. Tag
`v3.0.0-beta1`, mark the GitHub release prerelease.

## 8. Proposed 3.0.0-beta architecture

### 8.1 One DX12 video surface

New `Dx12Video` (name TBD):

- Owns `ID3D12Device` (same adapter as the D3D11 decoder), `ID3D12CommandQueue`,
  allocator/list, fence, flip-model swapchain for the stream HWND.
- `DXGI_SWAP_CHAIN_FLAG_ALLOW_TEARING | FRAME_LATENCY_WAITABLE_OBJECT`,
  `SetMaximumFrameLatency(1)`.
- Simple fullscreen blit pipeline (root signature, VS/PS, sampler) with
  letterbox viewport.
- Source paths:
  - preferred: import the decoder's D3D11 video-processor output as a shared NT
    handle (`D3D11_RESOURCE_MISC_SHARED_NTHANDLE`) and sample it directly;
  - fallback: upload tightly packed RGBA to a default texture.
- Present-on-arrival at buffer 0; optional phase gate when `vsync` on.

This surface is the only presenter used in Watch. The existing D3D11
`Presenter` stays for the shell/legacy UI.

### 8.2 Native AI stages (all in-process, DX12)

Order: decode texture → SR (DLSS/FSR) → NR (optional) → FG (DLSS-G/FSR FG) → present.

- **NVOFA** (`NvOf`): one D3D12 instance at the SR/FG input size, 4 px grid,
  forward flow + cost; register input textures with fences. Provides MVs for
  both DLSS SR and DLSS-G. Only on NVIDIA; on AMD use zero MVs + reset for SR,
  and a GPU block-matching shader later for FSR FG.
- **DLSS SR**: NGX D3D12 on the same device, real MVs + flat depth, no reset
  unless scene cut; output directly to a DX12 texture.
- **FSR SR**: FSR API context, real/zero MVs, `reset` policy per vendor;
  output to a DX12 texture. Log the actual provider version
  (`ffxQueryGetProviderVersion`) so the UI can show 4.1.2 vs 3.1.6.
- **NR**: keep the existing worker for beta 1 (it is already DX12 internally),
  or integrate `nvngx_dlssnr.dll` in-process later if its ABI is confirmed.
  The note says "Neural runs on DX12", which is true for the worker.
- **DLSS-G**: native NGX feature 11, offscreen OutputReal/OutputInterpolated,
  `MultiFrameCount` 1..`MultiFrameCountMax`. On RTX 40 that is 2x; RTX 50 can
  do 3x–6x.
- **FSR FG**: FSR FG 4.0.2 / 3.1.6 swapchain on the same DX12 swapchain once
  the surface exists. Because the surface is ours, the swapchain API is usable
  without a second window. Beta 1 may ship SR + DLSS-G first, FSR FG second.

### 8.3 Pacing / drop policy

- One present per refresh when the source is at or below refresh; drop the
  oldest *unsent* frame, never the one already in the flip queue.
- Track `present_misses`, `PresentCount` vs `PresentRefreshCount`, and the
  source cadence; expose the real numbers.
- At 30 fps content with FG, feed unique frames only (fix duplicate detection:
  use a downscaled 64×36 signature with a perceptual threshold, not exact hash).
- At buffer 0, keep at most one spare and do not present duplicates.

### 8.4 UI

- Upscaling: `Backend = Auto / DLSS / FSR`; quality; output; note
  "Upscaling: DX11 or DX12".
- Frame Gen: `Backend = Off / DLSS-G / FSR FG`; note "DX12 only".
- Neural: note "DX12 only".
- Diagnostics: "Frame Gen: DX12 · Neural: DX12 · Upscaling: DX11/DX12",
  NVOFA status, FSR provider version, actual multiplier, dropped inputs.
- Optimize: NVIDIA → DLSS; AMD → FSR; Intel → FSR 3.1.6 fallback.

### 8.5 Release

- `CMakeLists.txt` 3.0.0; package `amd-fsr` runtime; README/notes.
- Tag `v3.0.0-beta1` as prerelease; keep `dist\_floor-2.7.0` for the delta.
- The site gets a short 3.0.0 note only after the build is stable.

## 9. Open questions for tomorrow

1. Do we ship Agility SDK `D3D12Core.dll` so FSR 4 can run on AMD, or accept
   the inbox runtime with a possible 3.1.6 fallback? (Needed for true FSR 4.)
2. NR: keep the worker for 3.0.0-beta, or reverse `nvngx_dlssnr.dll` ABI now?
3. FSR FG on AMD: implement a GPU optical-flow shader, or ship FSR FG only
   where NVOFA exists (NVIDIA) and zero-MV FG elsewhere?
4. Do we keep `veyla-classic.exe` / `veyla-legacy.exe` in the package? They
   carry the old D3D11/VFG paths and add confusion to "pure DX12".
5. 4K: allow native 4K FG on RTX 40 (no worker cap) and test VRAM/perf.
6. Beta channel: mark the release prerelease and require
   `general.update_channel = 1`, or ship it as a normal release labelled beta?
